# ADR 작성 가이드

ADR(Architecture Decision Record)은 레포지토리 전역 또는 특정 앱의 durable한 설계 결정을 기록한다.

## 언제 쓰는가

- 이 가이드는 [문서 작성 가이드라인](./documentation-guidelines.md)을 ADR이라는 문서 종류에 특화한 것이다.
  - 언어 쌍, metadata 같은 일반 문서 정책은 ADR에도 그대로 적용된다.
- 미래의 독자에게 설명할 만한 실질적 tradeoff가 있는 durable한 설계 결정만 ADR로 기록한다.
- 테스트로 이미 고정되는 통상적인 구현 선택에는 ADR을 쓰지 않는다.

## 위치와 번호

- 채택된 순서대로 `0001`부터 번호를 매긴다.
- 레포지토리 전역 결정은 `docs/en/adr/` 아래에 두고, `docs/ko/adr/`와 쌍을 이룬다.
- 앱 범위 결정은 `apps/*/docs/en/adr/` 아래에 두고, `apps/*/docs/ko/adr/`와 쌍을 이룬다.
- 쌍 맞추는 규칙 자체는 [언어 쌍](./documentation-guidelines.md#언어-쌍)을 따른다.

## 구조

- ADR 하나 = 결정 하나다.
  - 서로 관련 없는 결정은 별도 ADR로 나눈다.
- 제목 형식: `NNNN: <짧은 결정 문구>`.
  - 문제가 아니라 결정을 이름으로 삼는다.
- 필수 섹션은 순서대로 `Status`, `Context`, `Decision`, `Consequences`다.
  - `Status`는 `Proposed`, `Accepted`, `Superseded by ADR-NNNN`, `Deprecated` 중 하나만 쓴다.

## 작성 스타일

- 모든 섹션은 산문 단락이 아니라 중첩된 `-` 목록으로 작성한다.
  - ADR의 역할은 매끄럽게 끝까지 읽히는 글이 아니라, 결정의 이유를 빠르게 찾을 수 있게 하는 것이다.
  - 목록 항목 하나에 아이디어 하나만 담는다. "그리고"로 두 주장을 묶은 항목은 나눈다.
  - 사실이나 결정은 최상위 목록 항목에 쓰고, 그 이유·trade-off·예시는 바로 아래 중첩 항목에 쓴다.

## 섹션별 내용

- `Context`: 그 결정을 필요하게 만든 사실과, 기각한 대안 및 그 이유만 적는다.
  - 배경 설명은 반복하지 말고 정책 문서로 링크한다.
- `Decision`: 결정된 내용을 독자가 바로 행동에 옮길 수 있는 목록으로 적는다.
  - 예시 코드는 의도를 보여주기 위한 것이지 실제 구현이 아니다.
- `Consequences`: 이 결정 이후 성립하는 사실을, 얻는 것과 감수하는 비용으로 나눠 적는다.
  - 감수하는 비용 항목은 비용 이름만 적지 말고 왜 감수할 만한지를 반드시 함께 적는다.

## 예시

Before (산문, 이유가 묻혀 있음):

> 서버 쪽 배치 diff 엔드포인트를 대안으로 검토했지만, sync policy에서 v1 범위의 신규 서버 배치 엔드포인트를 이미 배제한 것과 같은 이유로 보류했다 — 개인 단일 사용자 배포에서 신뢰된 클라이언트가 하나뿐인 상황이라, 추가 서버 표면을 늘릴 근거가 아직 없다.

After (목록, 이유가 바로 보임):

- 서버 쪽 배치 diff 엔드포인트를 대안으로 검토했다.
  - 기각: 정책의 기존 "신규 서버 배치 엔드포인트 없음" 결정과 같은 이유 — 신뢰된 클라이언트가 하나뿐인 개인 배포라, 서버 표면을 늘릴 근거가 아직 없다.
