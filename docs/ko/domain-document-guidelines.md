# 도메인 문서 작성 가이드라인

## 적용 범위

- `docs/ko/domain/`의 용어집과 bounded context 문서에 적용한다.
  여기서 정하지 않은 것은 [문서 작성 가이드라인](./documentation-guidelines.md)을 따르고, 둘이 다르면 이 문서를 따른다.
  - 도메인 문서는 기능을 설계하고 테스트 케이스를 뽑는 기준이다. 다른 문서보다 해석이 하나로 정해져야 한다.

## 문서 구성

- bounded context 문서는 전체 그림을 먼저, 규칙을 나중에 둔다. 섹션 순서는 아래와 같다.
  - 읽는 사람은 개념이 어떻게 이어지는지 알아야 규칙 하나하나가 왜 있는지 이해한다.
    규칙 목록만으로는 규칙들이 어떤 구조 위에 놓이는지 보이지 않는다.
- `## 개요`: 이 bounded context가 무엇을 정하는지와 무엇을 다루지 않는지를 두세 줄로 쓴다.
- `## 개념 구조`: 주요 개념이 어떻게 이어지는지 mermaid 그림과 짧은 설명으로 쓴다.
  - 첫 그림은 bounded context 전체를 한눈에 보여 준다. 한 부분의 관계가 많아 첫 그림이 복잡해지면
    그 부분은 첫 그림에 선 하나로 남기고, `###` 소제목 아래 따로 그린다.
    - 숲을 보는 그림에 세부 관계가 섞이면 선이 엉켜 중심 개념이 묻힌다.
  - 개념의 정의는 용어집에 있다. 여기서는 개념 사이의 관계만 쓴다.
  - 상자는 세 가지 무게로 나눈다. 이 bounded context의 중심 개념은 `core`, 나머지 개념은 `base`,
    다른 bounded context의 개념은 `outside`다. 세 `classDef`는 모든 문서에서 같은 값을 쓴다.
    - 모든 상자가 같은 무게면 무엇을 중심으로 읽어야 하는지 그림이 말하지 않는다.
  - 개수가 정해진 관계는 선 위에 `1 : N`, `0..1 : N`처럼 적는다.
- `## 생애`: 상태가 바뀌는 개념이 있을 때만 둔다. 어떤 상태가 있고 무엇으로 바뀌는지 mermaid 그림으로 쓴다.
- `## ... 규칙 (<섹션 이름>)`: 규칙 섹션은 그 규칙이 다루는 대상으로 나누고, 중심 개념부터 세부 순서로 둔다.
  예: `## 동기화 규칙 (sync)`, `## 검색 규칙 (search)`
  - 섹션 이름은 규칙 ID에 들어간다. 정하는 법은 [규칙 ID](#규칙-id)에 있다.
  - 섹션 첫 줄에는 그 섹션이 무엇을 정하는지 한 문장으로 쓴다. 이 문장에는 ID를 붙이지 않는다.
  - 첫 줄 아래에는 그 섹션의 규칙을 요약한 `| ID | 규칙 |` 표를 둔다. ID 칸은 규칙 헤딩으로 가는 링크이고,
    규칙 칸은 그 규칙의 규칙 문장과 같다. 행 순서는 아래 규칙 헤딩의 순서와 같다.
    - 이유와 예를 건너뛰고 섹션의 규칙만 한눈에 읽게 한다.
    - 표는 손으로 쓰지 않고 `pnpm docs:rule-tables`로 만든다. 표가 규칙 본문과 다르면 `pnpm docs:check`가 실패한다.
      같은 문장을 두 곳에 손으로 적으면 한쪽만 고쳐져 어긋난다.
- 개요, 개념 구조, 생애에는 규칙을 쓰지 않는다. 지켜야 하는 것은 규칙 섹션에만 쓰고, 필요하면 ID로 가리킨다.
  - 같은 규칙이 두 곳에 적히면 한쪽만 고쳤을 때 어긋난다.

## 용어집

- 용어는 [용어집](./domain/glossary.md) 한 곳에서 정의한다. bounded context 문서에는 용어 정의를 두지 않는다.
  - 한 용어를 여러 bounded context가 쓴다. 예: source는 `library`가 정하고 `ingestion`이 쓴다.
    문서마다 정의하면 정의가 갈라진다.
- 한 용어는 프로젝트 전체에서 뜻이 하나다. bounded context마다 뜻이 달라야 하면 다른 용어를 만든다.
  - API, UI, Obsidian 플러그인이 같은 규칙을 함께 지킨다. 같은 말이 앱마다 다른 뜻이면 같은 규칙인지 알아볼 수 없다.
- 용어집은 그 용어를 정하는 bounded context마다 `## <bounded context>` 섹션으로 나눈다.
- 용어는 "이름(코드 이름): 정의" 형식의 목록 항목으로 적고, 코드 이름은 코드 표기로 쓴다.
  정의는 "~이다"로 끝나는 한 문장이다. 예: `` - fingerprint(`SourceFingerprint`): 임베딩이 읽는 입력의 hash다. ``
  - 코드 이름은 문서와 코드를 잇는다. 코드에 없는 개념은 코드 이름을 적지 않는다.
- 정의에는 그것이 무엇인지만 쓴다. 지켜야 하는 것은 bounded context 문서의 규칙에 쓴다.
  - 예: "sync job은 source의 한 버전을 임베딩하도록 요청한 기록이다"는 정의이고,
    "sync job의 저장 상태는 대기, 완료, 실패 중 하나여야 한다"는 규칙이다.
  - 정의와 규칙이 섞이면 규칙을 찾을 때 용어집까지 뒤져야 하고, 두 곳의 규칙이 어긋날 수 있다.
- 정의 아래 중첩 항목에는 예, 헷갈리기 쉬운 다른 용어와의 차이, 쓰지 않는 말만 적는다.
  - 예: post는 source와 다르다. 발행하지 않은 source도 있다.

## 규칙 문장

- 규칙 하나는 문장 하나로 쓴다. 주어는 용어집의 용어이고, 술어는 아래 넷 중 하나다.
  - 의무: "~해야 한다". 예: source 업로드는 파일 내용 전체를 담아야 한다.
  - 금지: "~할 수 없다", "~일 수 없다". 예: 처리 중은 sync job의 저장 상태가 될 수 없다.
  - 조건부 허용: "~일 때만 ~할 수 있다". 예: vault 파일은 frontmatter `sheska`가 YAML boolean `true`일 때만 동기화 대상이 될 수 있다.
  - 허용: "~할 수 있다". 예: source는 임베딩이 끝나기 전에도 발행할 수 있다.
  - 술어가 "~한다"이면 반드시 지킬 규칙인지 보통 그렇다는 설명인지 갈린다.
- 주어를 화면, 버튼, 서버 같은 구현 요소로 쓰지 않는다.
  - 예: "검색 화면은 발행하지 않은 source를 빼고 보여 준다"가 아니라 "발행하지 않은 source는 검색 결과에 나올 수 없다"
  - 화면을 주어로 쓰면 구현 하나를 적은 것이 되어, API나 다른 화면에서 같은 규칙을 지켜야 하는지 알 수 없다.
  - 동기화 클라이언트처럼 용어집에 있는 행위자는 주어가 될 수 있다. 누가 판단하는지가 규칙의 내용일 때 그렇다.
- 규칙 문장에는 용어집의 용어만 쓴다. 필요한 말이 용어집에 없으면 용어집에 먼저 더한다.
  - 같은 개념을 문서마다 다른 말로 부르면 같은 규칙인지 알아볼 수 없다.
- 지켰는지 판단할 수 있게 쓴다. "가급적", "적절히", "빨리"처럼 기준이 없는 말을 쓰지 않고 수와 경계를 적는다.

## 규칙 형식

- 규칙 하나는 `### <ID> <제목>` 헤딩 하나로 시작하고, 그 아래 줄에 규칙 문장을 쓴다.
  그 아래에는 `이유:`, `예:`, `참고:`로 시작하는 목록 항목만 둔다.
  - 읽는 사람은 제목만 훑어 섹션에 어떤 규칙이 있는지 알고, 필요한 규칙에서만 문장과 이유를 읽는다.
    문서 목차와 편집기의 개요에도 규칙이 하나씩 보인다.
  - 이유와 예를 구분해 적으면 규칙을 고칠 때 무엇을 함께 다시 봐야 하는지 보인다.
  - `참고:`에는 다른 문서나 규칙으로 가는 안내와, 규칙 때문에 막힌 일을 대신 어떻게 하는지만 쓴다.
    예: 실패한 sync job은 같은 내용을 다시 보내서 재시도한다.
- 제목은 규칙이 다루는 것을 짧게 줄인 말이다. 규칙 문장을 되풀이하지 않고, 술어 형식을 따르지 않는다.
  - 예: `### library.post-1 source 하나에 post 하나`
- 이유, 예, 참고에 해당하지 않는 내용이 남으면 규칙 문장에 넣거나 따로 규칙으로 세운다.

  예:
  ```markdown
  ### ingestion.embeddingModel-1 한 시점의 모델
  한 시점에 허용하는 임베딩 모델은 둘 이상일 수 없다.
  - 이유: 모델이 다르면 벡터를 서로 비교할 수 없다.
  ```

## 규칙 ID

- 규칙마다 `<bounded context>.<섹션 이름>-<번호>` 형식의 ID를 규칙 헤딩의 제목 앞에 붙인다.
  예: `library.sync-3`
  - 테스트 이름에 ID를 적어 규칙과 그 규칙을 검증하는 테스트를 잇는다.
  - ID만 보고 어느 문서의 어느 섹션 규칙인지 안다. 번호만 있으면 규칙을 찾아봐야 무엇에 대한 규칙인지 안다.
- bounded context는 문서 파일 이름에서 `.md`를 뺀 것을 그대로 쓴다.
  - 줄임말을 쓰면 줄임말과 context를 잇는 표가 따로 필요하다.
- 섹션 이름은 섹션이 다루는 용어의 코드 이름을 camelCase로 쓴다. 코드 이름이 없는 용어는 코드에서 그 개념을 부르는 이름을 쓴다.
  예: sync job 규칙은 `syncJob`, 검색 규칙은 `search`
  - 섹션 이름은 섹션 헤딩 끝 괄호 안에 적고, 한 문서 안에서 겹칠 수 없다.
  - 섹션 이름이 문서와 코드를 같은 말로 잇는다. `-`는 번호 앞에만 써서 섹션 이름과 번호를 구분한다.
- 결정표는 표 하나에 ID 하나다.
- 번호는 섹션마다 1부터 차례로 매기고, 새 규칙은 섹션의 어느 자리에 넣든 다음 번호를 받는다.
  - 번호를 문서 순서에 맞춰 다시 매기면 테스트와 이슈에 적힌 ID가 다른 규칙을 가리키게 된다.
- 지운 규칙의 번호는 다시 쓰지 않는다.
- 규칙을 다른 섹션으로 옮기면 새 ID를 붙인다.
  - 섹션 이름이 맞지 않는 ID는 틀린 곳을 가리킨다. 옮길 만큼 다루는 대상이 바뀌었다면 뜻도 바뀐 것이다.
- `pnpm docs:check`는 섹션 이름이 없거나 겹치는지와 ID가 속한 섹션에 맞는지 검사한다.
- 다른 규칙은 링크가 아니라 ID로 가리킨다. 예: (`library.sync-7`)
  - 헤딩 링크는 제목이 바뀌면 깨진다. ID는 규칙 하나를 바뀌지 않게 가리킨다.
- 표기만 고치면 ID를 그대로 두고, 뜻이 바뀌면 새 ID를 붙인다.
  - 옛 ID로 찾으면 바뀐 규칙에 맞춰 다시 볼 테스트가 모두 나온다.

## 결정표

- 조건 둘 이상의 조합으로 결과가 갈리면 문장 대신 결정표로 쓴다.
  - 문장으로 쓰면 빠진 조합과 겹치는 조합이 보이지 않는다.
- 결정표는 규칙 문장 아래에 둔다. 예: 규칙 문장 "source 업로드를 받으면 source의 가장 최근 sync job에 따라 아래 표대로 해야 한다." 아래에 표
- 결정표의 왼쪽 열은 조건, 오른쪽 열은 결과다. 어떤 입력이든 정확히 한 행에만 맞아야 한다.
  어떤 값이든 맞는 칸은 `-`로 적는다.
  - 두 행에 맞는 입력이 있으면 어느 결과를 따를지 정해지지 않는다.

  예: sync job을 만드는 경우

  | 가장 최근 sync job | 그 sync job의 fingerprint가 현재와 같음 | 결과 |
  |---|---|---|
  | 없음 | - | 새 sync job을 만든다 |
  | 완료 | 예 | 아무것도 하지 않는다 |
  | 완료 | 아니오 | 새 sync job을 만든다 |
  | 대기 | 예 | 새 sync job을 만들지 않고 그 sync job을 돌려준다 |
  | 대기 | 아니오 | 새 sync job을 만든다 |
  | 실패 | - | 새 sync job을 만든다 |

## 경계 예시

- 수나 기간의 경계가 있는 규칙에는 경계 바로 안쪽과 바깥쪽 예시를 함께 적는다.
  - 예: "source 제목은 100자를 넘을 수 없다"는 규칙이면 100자는 되고 101자는 안 된다고 함께 적는다.
  - "이상"과 "초과", "이내"가 어디까지인지는 문장만으로 흔히 다르게 읽힌다. 예시가 해석을 하나로 고정한다.
- 예시는 규칙 아래 `예:` 항목이나 입력과 결과의 표로 쓴다. Given/When/Then 형식은 쓰지 않는다.
  - 예시를 문서에서 실행하지 않는다. 실행하는 예시는 테스트 코드에 있다.
