# 도메인 문서 작성 가이드라인

도메인 문서는 기능을 설계하고 테스트 케이스를 뽑는 기준이라 해석이 하나로 정해져야 한다.
여기서 정하지 않은 것은 [문서 작성 가이드라인](./documentation-guidelines.md)을 따른다.

## 문서
- `docs/ko/domain/`에는 용어집(`glossary.md`) 하나와 bounded context마다 규칙 문서 하나를 둔다.
  파일 이름은 bounded context 이름이다. 예: `library.md`
- bounded context 문서는 `## 개요`, `## 개념 구조`, `## 생애`, 규칙 섹션 순서로 둔다. 생애는 상태가 바뀌는 개념이 있을 때만 둔다.
  - 개념이 어떻게 이어지는지 알아야 규칙 하나하나가 왜 있는지 이해한다.
- 개념 구조의 mermaid 그림은 상자를 세 무게로 나눈다. 중심 개념은 `core`, 나머지 개념은 `base`, 다른 bounded context의 개념은 `outside`다.
  - 첫 그림이 복잡해지면 한 부분을 첫 그림에 선 하나로 남기고, `###` 소제목 아래 따로 그린다.
- 지켜야 하는 것은 규칙 섹션에만 쓴다. 개요, 개념 구조, 생애에서는 규칙 ID로 가리킨다.
- 요구사항, 기능 목록, 일정은 쓰지 않는다.

## 용어집
- 용어는 용어집 한 곳에서 정의한다. bounded context 문서에는 정의를 두지 않는다.
- 한 용어는 프로젝트 전체에서 뜻이 하나다. 뜻이 달라야 하면 다른 용어를 만든다.
  - API, UI, Obsidian 플러그인이 같은 규칙을 함께 지킨다. 같은 말이 앱마다 다른 뜻이면 같은 규칙인지 알아볼 수 없다.
- 용어집은 그 용어를 정하는 bounded context마다 `## <bounded context>` 섹션으로 나눈다.
- 용어는 `` - 이름(`코드 이름`): ~이다. `` 형식으로 쓴다. 코드에 없는 개념은 코드 이름을 적지 않는다.
- 정의에는 그것이 무엇인지만 쓰고, 지켜야 하는 것은 규칙으로 쓴다.
  - 예: "sync job은 source의 한 버전을 임베딩하도록 요청한 기록이다"는 정의이고, "sync job의 저장 상태는 대기, 완료, 실패 중 하나여야 한다"는 규칙이다.
- 정의 아래 중첩 항목에는 예, 헷갈리기 쉬운 다른 용어와의 차이, 쓰지 않는 말만 적는다.

## 규칙 문장
- 규칙 하나는 문장 하나로 쓴다.
- 술어는 "~해야 한다", "~할 수 없다", "~일 때만 ~할 수 있다", "~할 수 있다" 중 하나로 쓴다.
  - "~한다"로 쓰면 반드시 지킬 규칙인지 보통 그렇다는 설명인지 갈린다.
- 규칙 문장에는 용어집의 용어만 쓴다. 화면, 버튼, 서버를 주어로 쓰지 않는다.
  - 예: "검색 화면은 발행하지 않은 source를 빼고 보여 준다"가 아니라 "검색 결과에는 post만 나올 수 있다"
  - 동기화 클라이언트처럼 용어집에 있는 행위자는 주어가 될 수 있다. 누가 판단하는지가 규칙의 내용일 때 그렇다.
- "가급적", "적절히"처럼 기준 없는 말 대신 수와 경계를 쓴다. 경계가 있으면 바로 안쪽과 바깥쪽 예를 함께 적는다.
  - 예: source 제목은 100자를 넘을 수 없다. 100자는 되고 101자는 안 된다.
- 조건 둘 이상의 조합으로 결과가 갈리면 문장 대신 결정표로 쓴다. 어떤 입력이든 한 행에만 맞아야 하고, 아무 값이나 맞는 칸은 `-`로 쓴다.
  - 문장으로 쓰면 빠진 조합과 겹치는 조합이 보이지 않는다.

## 규칙 형식
- 규칙 섹션은 `## <대상> 규칙 (<섹션 이름>)`으로 두고, 첫 줄에 그 섹션이 무엇을 정하는지 한 문장으로 쓴다. 예: `## 동기화 규칙 (sync)`
- 규칙마다 `### <제목>`을 두고, 규칙 문장은 그 아래 리스트 항목 하나로 쓴다. 규칙 문장 끝에 `<!-- nocap: <규칙 ID> -->`를 붙인다.
  - 제목은 규칙이 다루는 것을 짧게 줄인 말이다. 규칙 문장을 되풀이하지 않는다.
- `이유:`·`예:`·`참고:` 항목과 결정표는 규칙 문장 항목 안에 들여 쓴다.
  - `참고:`에는 다른 규칙으로 가는 안내와, 규칙 때문에 막힌 일을 대신 어떻게 하는지만 쓴다.

```md
### 한 시점의 모델
- 한 시점에 허용하는 임베딩 모델은 둘 이상일 수 없다. <!-- nocap: ingestion-embeddingModel-1 -->
  - 이유: 모델이 다르면 벡터를 서로 비교할 수 없다.
```

## 규칙 ID
- 규칙 ID는 `<bounded context>-<섹션 이름>-<번호>`다. 섹션 이름은 그 용어의 코드 이름을 camelCase로 쓴다.
  예: `library-sync-3`
  - 테스트는 `// nocap: <규칙 ID>` 태그로 규칙과 잇는다. 규칙 여럿을 검증하면 태그를 한 줄에 하나씩 쌓는다.
  - `pnpm rules:check`는 테스트가 없는 규칙과 없는 규칙을 가리키는 태그를 알린다. ID가 형식과 섹션에 맞는지는 리뷰에서 본다.
- 한 번 붙인 ID는 바꾸거나 다시 쓰지 않는다. 테스트와 이슈에 적힌 ID가 다른 규칙을 가리키면 안 된다.
  - 새 규칙은 섹션의 어느 자리에 넣든 다음 번호를 받는다. 지운 규칙의 번호는 비워 둔다.
  - 뜻이 바뀌거나 다른 섹션으로 옮긴 규칙은 새 ID를 받는다. 표기만 고치면 ID를 그대로 둔다.
- 다른 규칙은 헤딩 링크가 아니라 ID로 가리킨다. 예: (`library-sync-7`)
