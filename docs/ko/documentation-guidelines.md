# 문서 작성 가이드라인

오래 유지되는 프로젝트 Markdown 문서가 컨벤션, 프로젝트 동작, 장기적인 프로젝트 이해를 정의한다면 영어 문서와 한글 문서를 쌍으로 관리한다.
쌍 문서는 같은 정책을 설명해야 한다.

## 동기화 정책

- 영어 문서와 한글 문서는 쌍을 이루는 정책 문서다.
- 쌍 문서가 충돌할 때 특정 언어가 자동으로 우선하지 않는다.
- 쌍 문서가 충돌하면 영어와 한글 중 의도한 정책을 선택하고 같은 변경 단위에서 양쪽 문서를 모두 수정해야 한다.
- 충돌을 해결한 뒤 한쪽 언어를 낡은 상태로 남겨 두면 안 된다.

## 적용 범위와 예외

- 이 가이드라인은 루트 문서, 저장소 전역 문서, 앱 문서, 유지보수되는 도구 README를 포함한 오래 유지되는 프로젝트 Markdown 문서에 적용한다.
- `AGENTS.md` 같은 agent instruction file은 사람이 읽는 문서가 아니라 실행 지시문이므로 언어 쌍을 요구하지 않는다.
- `.codex/temp/` 아래 파일처럼 임시 또는 숨김 작업 노트는 제외한다.
- 생성 문서, 짧은 local note, 범위가 좁은 tool-specific file은 쌍 문서가 프로젝트 이해를 개선하지 않고 유지보수 비용만 늘린다면 단일 언어로 둘 수 있다.

## 문서의 역할

- 이 프로젝트는 문서를 engineering harness의 일부로 다룬다.
- 문서는 feedforward guidance를 제공한다.
  - 구현 전에 의도, 경계, mental model, tradeoff, 리뷰 기준을 설명해서 판단을 형성한다.
- static analysis, 테스트, type check, generator, CI는 feedback control이자 verification gate다.
  - 구현 중이거나 구현 후에 구체적이고 정형적이며 반복 가능한 요구사항을 검증한다.
- 문서는 자동화가 context를 잘 표현하지 못하는 영역에서 판단을 안내해야 한다.
- feedback control이나 verification gate가 이미 보장하는 긴 기계적 규칙 목록을 문서가 반복해서는 안 된다.
  - 기계적 요구사항이 중요하다면, 강제되는 모든 세부사항을 다시 적기보다 그 요구사항이 왜 존재하는지, 언제 중요한지, 어디에서 검증되는지를 설명한다.
- 자동 검증이 도움을 주기 전에 사람이나 agent가 판단해야 하는 규칙이거나, 위반 시 정책, 정확성, 유지보수 위험이 생기는 규칙에만 영어 문서에서 `MUST`를 사용한다.
- context에 따라 달라지는 구현 선택지는, 나중에 자동 검사나 테스트가 정확한 형태를 잡아낼 수 있다면 유연한 지침을 선호한다.

## 언어 쌍

- 언어 기준 디렉터리 이름을 쓴다 — 영어 문서는 `en`, 한글 문서는 `ko`.
- durable한 컨벤션 문서는 같은 상대 경로와 파일명을 가진 반대 언어 문서를 반드시 가져야 한다.
  - `docs/en/`은 `docs/ko/`와 짝을 이룬다.
  - `apps/*/docs/en/`은 `apps/*/docs/ko/`와 짝을 이룬다.
- 언어 디렉터리 밖의 공개 Markdown 파일이 오래 유지되는 사용자 또는 maintainer 대상 문서라면, 영어를 기본 파일로 두고 한글은 `*.ko.md`로 두는 것을 권장한다.
  - 예: `README.md`와 `README.ko.md`.

## 동기화

- 영어 문서와 한글 문서는 같은 제목 계층과 주요 섹션 순서를 반드시 유지해야 한다.
  - 제목 문구는 번역할 수 있다. 정확한 단어까지 일치시킬 필요는 없다.
- 문장별 직역은 필수가 아니다.
  - 한글 문서는 [작성 스타일](#작성-스타일)에 따라 영어 문서와 다른 예시·순서·부연 설명을 쓸 수 있다.
- 규칙, 예외, 명령어, 경로, API 이름, type 이름은 양쪽 문서에서 같은 의미를 가져야 한다.
- 한 언어 문서를 변경하면 같은 PR 또는 변경 단위에서 쌍을 이루는 다른 언어 문서도 함께 변경해야 한다.

## 메타데이터

- 오래 유지되는 컨벤션 문서는 제목, 언어, audience 또는 scope, 쌍 문서를 식별하는 YAML frontmatter나 그에 준하는 metadata를 포함하는 것을 권장한다.
  - 쌍 문서 식별은 영어 문서에서 `translation`, 한글 문서에서 `source`와 `last_synced`로 한다.
- 같은 문서군 안에서는 metadata key를 일관되게 유지하되, reader, tool, maintenance workflow가 사용하지 않는 key는 추가하지 않는다.
- `read_when`은 문서가 index에서 라우팅되고 그 trigger가 문서 자체에도 유용할 때만 포함한다.
- `related`는 함께 읽어야 하는 문서가 명확할 때만 포함한다.
- 문서 간 metadata link에는 상대 경로를 사용한다.

## 문서 라우팅

- 문서는 주제만이 아니라 언제 읽어야 하는지를 기준으로 구성한다.
- 각 문서는 `index.md`에서 라우팅할 수 있는 명확한 작업 조건을 가진다.

## 문서 구조

- 제목은 `#` 하나, 주요 규칙 그룹은 `##`을 쓴다.
  - 하나의 판단 영역에 속한 규칙·rationale·예외·예시를 묶을 수 있을 때만 `###` 이상으로 더 들어간다.
- 섹션은 독자에게 먼저 필요한 순서로 배치한다.
  - 범위·동기화 정책 규칙을 작업별 규칙보다 앞에 둔다.
  - 기본 규칙을 예외보다 앞에 둔다.
- 독자가 내려야 하는 판단을 기준으로 묶는다. artifact 종류, 시간 순서, 규칙을 발견한 순서로 묶지 않는다.
  - 관련 없는 규칙을 모아두기 위한 섹션은 만들지 않는다.
- index·routing 문서는 얕게 유지한다.
  - 세부 정책을 반복하지 말고 상세 문서로 라우팅한다.

## 규칙 품질

- 재사용 가능한 원칙, 장기 컨벤션, 리뷰 기준, 유지보수 이유가 있을 때만 규칙을 추가한다.
  - 임시 저장소 상태, 일회성 migration 공백, 현재의 특수한 상황을 땜질하기 위한 규칙은 추가하지 않는다.
- 규칙을 추가하기 전에 같은 판단을 이미 소유한 기존 섹션이 있는지 확인한다.
  - 있다면 정책을 다른 곳에 반복하지 말고 그 섹션을 갱신한다.
- 임시 대응은 작업 노트, PR 설명, 또는 해당 변경 context에 둔다.
  - 컨벤션 문서로 승격하지 않는다.
- 장기적으로 유지할 목표 동작을 직접 쓴다.
  - 이전 pattern이 현재 변경에만 중요하다면 `이전 X pattern을 유지하지 말고 Y를 사용한다`보다 `Y를 사용한다`를 선호한다.
  - 현재 또는 과거 구현 detail은 오래 유지되는 경계, tradeoff, migration rule을 설명할 때만 언급한다.

## 작성 스타일

### 영어 문서

- 영어 문서는 처음부터 끝까지 읽는 사람이 아니라, 필요한 섹션만 골라 읽는 LLM 에이전트를 위해 쓴다.
  - 섹션은 라우팅되어 개별적으로 읽힌다.
  - 각 섹션이 그 자체로 완결되도록 주어를 명시하고, 앞선 섹션의 맥락에 기대지 않는다.
- 모든 규칙을 산문이 아니라 `-` 목록으로 쓴다.
  - 결론(규칙)을 최상위 항목에 쓰고 근거는 그 아래 중첩 항목에 둔다.
  - 훑어보는 사람이 이유보다 결론을 먼저 보게 한다.
- 같은 개념은 항상 같은 용어로 부른다.
  - 문장을 다채롭게 하려고 표현을 바꾸지 않는다.
  - 에이전트가 개념을 매칭할 때는 사람이 다채로운 문장에서 얻는 이득보다 일관된 용어에서 얻는 이득이 크다.
- 규칙이 적용되는 범위와 조건을 암묵적으로 남기지 말고 명시한다.
- 지시 대상이 멀거나 모호한 대명사를 피한다.
  - 항목이 단독으로 읽힐 수 있다면 "이것", "그것" 대신 주어를 반복해서 쓴다.
- 정적 검사로 보장되는 규칙은 검사 내용만 반복하지 말고, 규칙의 의도를 설명한다.

### 한글 문서

- 한글 문서는 영어 문서의 번역본이 아니라 개발자 동료가 읽는 문서다.
  - 자연스럽게 쓴다.
- 영어 문장 구조를 그대로 옮기기보다 한국어 어순과 자연스러운 흐름을 우선한다.
- 코드, 명령어, 파일 경로, URL, frontmatter key, API 이름, type 이름, package 이름, identifier, product name은 원문 그대로 쓴다.
  - 한국어 기술 문서에서 영어 용어를 그대로 섞어 쓰는 건 자연스러운 일이지, 굳이 예외로 짚어야 할 규칙이 아니다.
- 한글 문서는 영어 문서와 다른 예시·순서·부연 설명을 써도 된다.
  - 단, 같은 정책만 전달되면 된다.

### 공통 규칙

- 문서는 역량 있는 구현자를 위한 지침으로 작성한다.
  - 직접적으로 쓰되, 모든 선호를 금지 규칙으로 바꾸지 않는다.
- 규칙에 tradeoff, 알려진 예외, 구현 context 의존성이 있다면 뉘앙스를 함께 설명한다.
- 긴 항목은 한 줄에 여러 절을 늘어놓지 말고 중첩 목록으로 나눈다.
  - 각 절은 그것이 보완하는 상위 항목보다 한 단계 아래에, 자신만의 줄을 갖는다.
