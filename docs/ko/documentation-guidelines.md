# 문서 작성 가이드라인

## 적용 범위

- 컨벤션, 프로젝트 동작, 장기적인 프로젝트 이해를 정의하는 오래 유지되는 Markdown 문서에 적용한다.
  루트 문서, 앱 문서, 유지보수되는 도구 README가 여기 해당한다.
- `AGENTS.md`, `CLAUDE.md` 같은 agent instruction 파일은 사람이 읽는 문서가 아니라 실행 지시문이므로 제외한다.
- 임시 작업 노트, 생성 문서, 범위가 좁은 tool-specific 파일도 제외한다.

## 언어

- 프로젝트 문서와 코드 주석은 한글로 쓴다. 문서를 언어별 쌍으로 관리하지 않는다.
- 저장소 밖 독자를 향하는 공개 파일은 예외다. 영어 파일을 기본으로 두고 한글은 `*.ko.md`로 둔다.
  - 예: `README.md`와 `README.ko.md`.
- 한글 문서 안에서도 identifier, type 이름, API 이름, 에러 코드, 파일 경로, package 이름, 굳어진 기술 용어는 원래
  표기 그대로 둔다. 번역하면 문서와 문서가 설명하는 코드 사이의 연결이 끊어진다.
- identifier가 아닌 일반 설명어와 추상 개념은 한국어로 쓴다.
  - 예: `architectural boundary`가 고정 용어로 쓰이는 경우가 아니라면 `아키텍처 경계`로 쓴다.
  - 한 문장에 영어 용어가 과하게 몰리면 문장을 나누거나 규칙 설명 부분을 한국어로 풀어쓴다.
- UI 문구, API 응답, 로그 메시지처럼 사용자나 운영자에게 전달되는 문자열은 주석이나 문서가 아니므로 적용 범위 밖이다.

## 문서의 역할

- 이 프로젝트는 문서를 engineering harness의 일부로 다룬다.
- 문서는 feedforward guidance다. 구현 전에 의도, 경계, mental model, tradeoff, 리뷰 기준을 설명해서 판단을 형성한다.
- 정적 분석, 테스트, type check, CI는 feedback control이자 verification gate다. 구체적이고 정형적이며 반복 가능한
  요구사항을 구현 중이나 구현 후에 검증한다.
- 자동화가 이미 강제하는 규칙 목록을 문서가 반복하지 않는다.
  - 규칙이 왜 존재하는지, 언제 중요한지, 어디에서 검증되는지를 쓰고 규칙 파일을 가리킨다.
  - 규칙을 두 곳에 적으면 반드시 갈라진다. 갈라진 문서는 없는 문서보다 나쁘다.
- 구현하지 않았거나 아직 결정하지 않은 정책은 문서로 만들지 않는다.
  - 아직 없는 문서의 목록도 관리하지 않는다. 그 메커니즘을 실제로 만드는 변경 단위에서 문서를 함께 쓴다.
- 자동 검증 전에 사람이나 에이전트가 판단해야 하고, 위반하면 정책·정확성·유지보수 위험이 생기는 규칙에만 강한
  표현을 쓴다.
- 맥락에 따라 달라지는 구현 선택지는, 나중에 검사나 테스트가 정확한 형태를 잡아낼 수 있다면 유연한 지침을 선호한다.

## 메타데이터

- frontmatter에는 `title`, `applies_to`를 둔다.
  - 문서가 index에서 라우팅되고 그 trigger가 문서 자체에도 유용할 때만 `read_when`을 둔다.
  - 함께 읽어야 하는 문서가 명확할 때만 `related`를 둔다.
- reader, tool, 유지보수 작업이 실제로 쓰지 않는 key는 추가하지 않는다.
- 문서 간 링크에는 상대 경로를 사용한다.

## 문서 라우팅

- 문서는 주제만이 아니라 언제 읽어야 하는지를 기준으로 구성한다.
- 각 문서는 `index.md`에서 라우팅할 수 있는 명확한 작업 조건을 가진다.
- index와 routing 문서는 얕게 유지한다. 세부 정책을 반복하지 말고 상세 문서로 라우팅한다.

## 문서 구조

- 제목은 `#` 하나, 주요 규칙 그룹은 `##`을 쓴다.
  - 하나의 판단 영역에 속한 규칙·rationale·예외·예시를 묶을 수 있을 때만 `###` 이상으로 더 들어간다.
- 섹션은 독자에게 먼저 필요한 순서로 배치한다. 적용 범위를 작업별 규칙보다, 기본 규칙을 예외보다 앞에 둔다.
- 독자가 내려야 하는 판단을 기준으로 묶는다. artifact 종류, 시간 순서, 규칙을 발견한 순서로 묶지 않는다.
  - 관련 없는 규칙을 모아두기 위한 섹션은 만들지 않는다.

## 규칙 품질

- 재사용 가능한 원칙, 장기 컨벤션, 리뷰 기준, 유지보수 이유가 있을 때만 규칙을 추가한다.
  - 임시 저장소 상태, 일회성 migration 공백, 현재의 특수한 상황을 땜질하는 규칙은 추가하지 않는다.
- 규칙을 추가하기 전에 같은 판단을 이미 소유한 기존 섹션이 있는지 확인한다.
  - 있다면 정책을 다른 곳에 반복하지 말고 그 섹션을 갱신한다.
- 임시 대응은 작업 노트, PR 설명, 해당 변경 맥락에 둔다. 컨벤션 문서로 승격하지 않는다.
- 장기적으로 유지할 목표 동작을 직접 쓴다.
  - 이전 pattern이 현재 변경에만 중요하다면 `이전 X pattern을 유지하지 말고 Y를 사용한다`보다 `Y를 사용한다`를
    선호한다.
  - 현재나 과거의 구현 detail은 오래 유지되는 경계, tradeoff, migration rule을 설명할 때만 언급한다.

## 작성 스타일

- 문서는 처음부터 끝까지 읽는 사람이 아니라, 필요한 섹션만 골라 읽는 개발자와 LLM 에이전트를 위해 쓴다.
  - 각 섹션이 그 자체로 완결되도록 주어를 명시하고, 앞선 섹션의 맥락에 기대지 않는다.
  - 지시 대상이 멀거나 모호한 대명사를 피한다. 항목이 단독으로 읽힌다면 "이것", "그것" 대신 주어를 반복한다.
- 모든 규칙을 산문이 아니라 `-` 목록으로 쓴다.
  - 결론(규칙)을 최상위 항목에 쓰고 근거는 그 아래 중첩 항목에 둔다.
- 같은 개념은 항상 같은 용어로 부른다. 문장을 다채롭게 하려고 표현을 바꾸지 않는다.
- 규칙이 적용되는 범위와 조건을 암묵적으로 남기지 말고 명시한다.
- 역량 있는 구현자를 위한 지침으로 쓴다. 직접적으로 쓰되, 모든 선호를 금지 규칙으로 바꾸지 않는다.
  - 규칙에 tradeoff, 알려진 예외, 구현 맥락 의존성이 있다면 뉘앙스를 함께 설명한다.
- 긴 항목은 한 줄에 여러 절을 늘어놓지 말고 중첩 목록으로 나눈다.
  - 각 절은 그것이 보완하는 상위 항목보다 한 단계 아래에, 자신만의 줄을 갖는다.
- Markdown 원문을 가로 스크롤 없이 읽기 쉽게 유지한다.
  - 구조적으로 나누기 어려운 일반 문장은 한 줄이 대략 120자를 넘어가는 시점에 줄바꿈한다.
    - 120번째 글자에서 기계적으로 자르지 말고 문장이 끝나는 지점에서 줄을 바꾼다.
  - 표, 코드 블록, URL처럼 줄바꿈이 가독성이나 정확성을 떨어뜨리는 문법은 줄바꿈하지 않아도 된다.
  - 목록의 한 항목을 여러 줄로 나눌 때는 이어지는 줄의 들여쓰기를 유지한다.
